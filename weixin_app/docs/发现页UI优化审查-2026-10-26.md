## 一、结论与裁决结果

### 1.1 总体判断

这一版已有明确的青墨气质、编辑式大标题、双列混合信息流和统一的 32rpx 页面边距，**不建议推倒重做，也不建议先换主色**。当前主要空间在四处：

1. **可读性**：辅助文字和未选导航过浅、偏小，玻璃卡又把内容压成灰蒙质感。
2. **内容优先**：顶部标题、搜索、AI 入口、频道连续占据较多首屏，真正内容出现偏晚。
3. **动作承诺**：部分卡片药丸写着“下载/打卡/去回答”，实际只进入详情页，和用户预期不完全一致。
4. **交互闭环**：搜索缺少可见关闭/清除，频道切换缺少结果反馈，读屏语义和小屏表现尚未验证。

本轮共整理 **12 项**：`P0` 3 项、`P1` 8 项、`P2` 1 项。用户已确认「按照建议方案执行」，因此 12 项均已落地或补上保护规则；真机项目仍单独列在第六章。

- 搜索框、AI 入口、底部发布入口都有明确的功能身份，不需要再新增模块。

## 二、证据口径与边界

- 截图为一次静态首屏，能确认留白、颜色、层级和文案；不能证明滚动深处、键盘态、小屏、大屏、Android 与 iOS 的真实表现。
- 对比度按 WCAG 相对亮度公式对静态色值计算。玻璃、阴影、抗锯齿会改变实际像素，因此文中数值用于发现问题，不作为最终真机验收值。
- 375pt 基准下，`20rpx ≈ 10px`、`32rpx ≈ 16px`、`80rpx ≈ 40px`。其他屏宽会随 rpx 等比变化。
- “P0”在本报告中指基础可用性或行为一致性，不等于视觉上最激进。
- 既有 `docs/前端视觉优化方案.md` 的品牌方向与像素契约仍作为约束：青墨主色、墨笔触 Tab、FAB 光池、渐变封面、云纹资产均不因本审查被否定。
- 第三章与第四章中的代码行号对应当天执行前的审查快照；执行后的实际改动、顺序和验证结果见第八章。

## 三、逐项审查

### D01｜P0｜功能型辅助文字过浅、偏小

**现象**：日期、未选频道、赞评数、宽卡人数、底部未选导航都明显发灰；底栏弱到接近禁用态。

**证据**：
- `app.wxss:15`：`--text3:#8A9890`；日期/元信息/底栏字号多处为 `20rpx`（`app.wxss:66、100、397`）。
- 静态对比度：`#8A9890` 对页面底 `#E1DAD2` 约 **2.17:1**；对当前玻璃卡合成底约 **2.14:1**；对纯白约 **3.01:1**。
- Tab 图标灰 `#96A49C` 对白约 **2.60:1**。
- 若换为 `#52615A`：对玻璃合成底约 **4.64:1**、页面底约 **4.71:1**、白底约 **6.53:1**。

**建议**：
- 把“功能型辅助文字”和“禁用/装饰文字”拆成两个语义：前者建议新增 `--text-meta`（候选 `#52615A`），后者才继续用 `--text3`。
- 日期、人数、赞评数、未选频道、底栏标签建议由 `20rpx` 提到 `22rpx`；空间允许再到 `24rpx`。不要只加深颜色而继续保留极小字号。
- 不建议直接把全局 `--text3` 改深：它还被大量装饰性文字复用，一刀切会削弱层级并影响全站；应先拆分语义，再决定是否全站推广。
- 搜索输入态仍保留 `32rpx`。搜索是主操作，不应为了“层级”缩小到难读。

**裁决**：J1。静态色值可确定，玻璃实际对比仍需真机复核。

### D02｜P0｜内容卡玻璃材质与纸卡契约冲突

**现象**：截图卡片呈灰蒙质感，边界主要靠白描边和大阴影；同一信息流内标题清楚，但正文像隔了一层脏玻璃。

**证据**：
- `app.wxss:95` 先定义纸白卡、`--r-xl:32rpx`、`--shadow-2`。
- 后置 `app.wxss:680` 又全局覆盖为 `rgba(217,217,217,.58)` + `blur(12rpx)` + 白边 + `24rpx 34rpx 102rpx` 大阴影 + `34rpx` 圆角 + `transition: all .5s`。
- 截图中的双列图文卡、问答宽卡均呈灰底；这与既有方案“磨砂只用于背后有滚动内容的悬浮件”的范围不一致。
- 静态检索当前 WXML 中 `.fcard` 类名只出现在发现页，适合先做页面级纠偏，而不是继续叠加全局后置样式。

**建议**：
- 方案 A（建议）：发现页内容卡恢复 `var(--card)`、`var(--r-xl)`、`var(--shadow-2)`，去掉整卡 `backdrop-filter` 和白描边；搜索弹层、输入 dock 等真正悬浮面继续保留玻璃。
- 方案 B：若想保留玻璃实验，只限定在少数卡片，并显式提供无 blur 的实底回退；不要默认铺满整条信息流。
- 同步把 `transition: all .5s` 收窄到 `transform/opacity/background-color`，避免无意触发布局属性过渡。
- 主要收益是可读性和一致性；去 blur 对 GPU 可能有利，但在没有帧率基线前不承诺具体性能数字。

**裁决**：J2。属于修复既有契约偏离，不建议再新增一层边框或阴影掩盖问题。

### D03｜P1｜首屏纵向节奏偏“头重”，AI 入口压过内容

**现象**：日期/大标题 → 搜索 → AI → 频道 → 信息流，内容约在截图高度 42% 处才开始；AI 入口本身占据一整块强视觉区域。

**证据**：
- `app.wxss:139–147`：AI 卡上下 padding `26/30rpx`，引文 `30/700`，比卡标题 `28/700` 更重；随后频道高 `80rpx`，信息流顶距 `24rpx`。
- `pages/discover/discover.wxss:7–10` 已压缩过头部间距；标题到搜索仅 `12rpx`，这里不建议继续挤。
- `pages/discover/discover.wxml:61–67` 的 AI 入口顺序和内容没有错，问题主要是留白和字重。

**建议**：
- 保守方案：AI 上下 padding 收至约 `20/24rpx`、底距 `16→8rpx`、信息流顶距 `24→16rpx`，合计上移约 **24–28rpx**；保留双行、顺序、32rpx 页面边距和所有触控区。
- 可选方案：把 AI 改成单行紧凑入口，可再释放高度，但会削弱“AI 学伴”作为核心卖点的展示。本轮未采用，保留为后续方向。
- 不建议缩页面标题、搜索高度、频道高度来换空间；这些是主操作或可读性资产。
- 不建议为了压层级把静态搜索提示从 `32rpx` 缩到很小；优先用留白和字重处理 AI 与内容的竞争。

**裁决**：J3。375px 设备上以“内容更早露出且热区不缩水”为验收，不只看上移像素数。

### D04｜P1｜封面面积、双列节奏与宽卡衔接

**现象**：标题写“实拍/实测”，封面却是一整块渐变；两张图文的封面约占卡片高度六成。双列不等高符合瀑布流预期，但双列后接全宽卡时，额外间距让节奏突然断一下。

**证据**：
- 封面色块高度 `300/336/288/312rpx` 分散在 `discover.wxml`；四套渐变在 `app.wxss:107–112`，云纹白色不透明度约 `.32`。
- `.falls` 为 2 列、列沟 `16rpx`、页边距 `32rpx`；普通卡底距 `24rpx`，宽卡另有 `margin-top:8rpx`（`app.wxss:94、95、114`）。
- `column-span:all` 的实际行为受渲染环境影响，截图只能证明当前设备上可见。

**建议**：
- 保留 32rpx 页面边距、16rpx 列沟和自然瀑布流，先统一宽卡前后的净间距为约 24rpx，不在普通卡间距上再叠加 8rpx。
- 封面候选高度收至 `200–240rpx`，云纹不透明度降至 `.12–.16`，饱和度降低约 20%；保留话题映射，不新增图片资源。
- 若强调“真实经验”，有真实图时优先真实图；无图图文帖可改为更紧凑的排版卡或低高度题图。是否改变既定的“渐变代理封面”方向，属于 J4，不是顺手改。
- 双列标题因卡片高度不同而不在同一基线，是瀑布流的正常结果；若你更想要杂志式整齐，应改成“成对双列 + 宽卡”的明确分组，而不是微调单个 margin。

**裁决**：J4。保留瀑布流是建议默认，不在本轮直接换栅格。

### D05｜P1｜底部发布钮与蓝/紫强调争夺焦点

**现象**：底部中央“+”是导航里最重的元素；截图中的蓝色“去回答”比较跳，搜索聚焦的紫色多层辉光（截图未展开）有进一步抢焦点的风险。

**证据**：
- FAB 大小 `96rpx`、上移 `32rpx`、白边/品牌阴影叠加（`app.wxss:404、567`），加号还有 `2s linear infinite` 的 `fab-flicker`（`app.wxss:748–749`）。
- 问答蓝 `#3641C4` / 浅蓝底 `#E9EBFA` 静态对比约 **6.54:1**，可读性不是问题，问题是行动色语义分散。
- 搜索聚焦使用 `#B56AFF/#8B5CF6` 与四层紫色阴影（`app.wxss:756–760`）。

**建议**：
- FAB 保留光池、`overflow:hidden`、顶部高光和既有品牌阴影；优先取消常态 2s 无限闪烁，必要时再把 96 缩至 88rpx。
- FAB 仍是主行动，不建议完全抹平；是否齐平改普通中间 Tab 是导航方向变更，放在 J5 裁决。
- 青墨继续承担主 CTA；问答蓝只保留问答语义（标签/次级操作），搜索紫色只作为瞬态反馈并减弱光晕强度。
- 不建议新增第三套实色行动按钮来“统一颜色”。

**裁决**：J5。蓝色可读性无需修；紫辉光和脉冲需要真机看动态效果。

### D06｜P0｜卡片药丸的动作承诺与实际结果不一致

**现象**：宽卡右侧呈现独立按钮形态的“去回答 / 下载 / 打卡”，但整张卡只有一个 `bind:tap`，实际都进入对应详情页，并没有直接完成回答、下载或打卡。

**证据**：
- `pages/discover/discover.wxml:93–100、116–160`：药丸是卡内文本，没有独立事件。
- `pages/discover/discover.js:55–58`：`goQa/goRes/goChk` 只做页面导航。
- `app.wxss:114–120`：`.w-pill` 被做成完整按钮外观，强化了“这是第二个动作”的预期。

**建议**：
- 方案 A（建议）：保留整卡单入口，把药丸改成真实结果的导航提示，如“查看问答 / 查看资料 / 查看打卡 ›”；整卡按压反馈保持一致。
- 方案 B：只有在确实支持直接回答/下载/打卡时才拆成独立按钮，使用独立热区、`catch:tap` 和成功/失败反馈；不要只改文案却仍只导航。
- 读屏时整卡只报一个“标题 + 目的地”的动作名称，不把药丸读成第二个按钮。

**裁决**：J6。代码事实可确定，无需等真机。

### D07｜P1｜搜索退出、清除与键盘反馈不闭环

**现象**：打开搜索后只能点遮罩关闭，关闭会清空关键词与结果；没有显式关闭或清除按钮。`confirm` 只执行过滤，没有收起键盘，结果区可能被键盘进一步压缩。

**证据**：
- `discover.wxml:16–58` 无关闭/清除控件；`discover.js:33–47` 的 `closeSearch` 同时清空关键词与结果，`runSearch` 不处理键盘。
- 搜索弹层 `discover.wxml:33` 高度按 `sdTop` 定位，结果区 `app.wxss:791` 最大高度 `52vh`；键盘弹出后的可视高度需真机确认。

**建议**：
- 打开态提供明确的“取消/关闭”；有关键词时提供清除入口，清除只处理关键词，不关闭面板、不丢焦点。
- 区分“关闭搜索”和“清除关键词”：遮罩关闭建议保留本次草稿（J8-A），显式“取消”再清空。
- 键盘搜索确认后收起键盘并保留输入与结果；无结果时仍保留可见的关闭路径。
- 共享的 `.sd-*` 样式服务四个页面，任何修改都要确认其他搜索页同步或加页面作用域，不能只测发现页。

**裁决**：J8。大部分是 WXML/JS 行为，不是纯配色修正。

### D08｜P1｜频道切换缺少结果范围和空态

**现象**：频道只有选中态，没有“当前筛选到底剩什么”的反馈。切到内容较少的频道时，可能出现突然变短或位置悬空，也可能没有空态兜底。当前“生活”实际只是显示图文卡，和“推荐”中的图文子集没有明确可理解的差别。

**证据**：
- `discover.js:26–30` 仅映射 `hide-photo/hide-qa/...`；`discover.wxss:1–5` 用 `display:none` 隐藏卡片。
- `discover.wxml:69–75` 只有频道文字，没有数量或结果区标题。

**建议**：
- 保留现有筛选架构，在筛选后提供轻量结果反馈，例如“问答 · 2 条”；无结果必须有空态，不能只留空白。
- 如果用户已经滚过内容顶部，切换频道后回到结果起点；仍在首屏内切换则不强制跳动。
- 明确“生活”的筛选规则；如果没有独立数据，不要把它包装成已生效的独立频道。
- 增加 JS/WXML 时只会在点击频道时 setData 一次，不涉及滚动回调；仍需按既有约定先算值再决定是否下发。

**裁决**：J9。是否常驻显示数量需要你定，不建议为数量新增大块头部。

### D09｜P1｜部分触控目标小于 44×44 CSS px

**现象**：头像、频道、热门词条的可点区域小于舒适触控尺寸；打开态“搜索”只有文字自身可点。视觉上的小药丸不应直接当作独立热区，因为当前整卡都可点。

**证据**：
- 头像 `80rpx`（约 40px，`app.wxss:68`）；频道自身高度 `80rpx`，但“生活”文字宽约 `56rpx`（`app.wxss:89`）；热门词高度 `60rpx`（`app.wxss:782`）。
- 打开态“搜索”是文本上的独立 `bind:tap`（`discover.wxml:26`），实际可点宽度更小。
- `.w-pill` 当前不是独立事件；若 D06 选 A，整卡热区已足够，不要再给它单独造小按钮。

**建议**：
- 只扩大点击盒，不放大视觉图形：头像与搜索提交区至少约 44×44px，热门词提升有效高度与垂直间距，频道增加左右 padding。
- 相邻热区之间保留间隙，避免扩大后互相覆盖。
- 若 D06 选 B 做真正独立动作，按钮必须同步达到 80rpx 热区，并做按压/成功/失败反馈。
- 320px 和单手操作要实机走查，不能只看截图。

**裁决**：属于执行项；与 D06 的选择联动。

### D10｜P1｜可点 view 缺少动作语义和状态

**现象**：卡片、头像、搜索条、AI 入口、频道、底栏、FAB 都是 `view` 绑定点击；选中状态、当前 Tab、未读红点主要靠视觉表达。屏幕阅读器用户可能不知道这些区域可点，也可能听到装饰云纹的冗余内容。

**证据**：
- `pages/discover/discover.wxml` 与 `components/tab-bar/tab-bar.wxml` 没有 `aria-*`。
- 频道“已选”、底栏当前页、消息未读点、头像红点均为纯视觉状态。
- 全项目 WXML 仅在 `post-detail` 与 `drafts` 各出现 1 处 `aria/role`，不是统一机制。

**建议**：
- 按目标基础库实际支持度使用 `aria-role`、`aria-label`、`aria-hidden`，不要照搬 Web 的 `tabindex/keydown`。
- 整卡给一个包含标题与目的地的动作名称；搜索、头像、FAB、底栏补名称；频道与当前 Tab 把“已选/当前”写进可访问名称；未读补“有未读消息”；纯装饰隐藏。
- 保留可见文字，不用 `aria-label` 替代标题；结果数与空态必须是真实可读文本。
- 必须用 iOS VoiceOver + Android TalkBack 验证，模拟器通过不算完成。

**裁决**：执行项。是否能在当前基础库稳定实现，需要真机确认后再全站推广。

### D11｜P1｜小屏、长文、字体放大与安全区尚未验收

**现象**：375px 下双列已偏紧；320px 时每列约 140px，扣掉卡内边距后标题只剩很窄的行宽。宽卡中图标、标题和右侧药丸同排，也更容易挤压。固定高度控件和底部固定 Tab 对大字模式、安全区的包容度还没有证据。

**证据**：
- `app.wxss:94–99` 双列、2 行截断；`app.wxss:114–127` 宽卡同排；`app.wxss:43、395、561、566–568` 固定底栏、200rpx 内容留白与安全区处理。
- `discover.wxml:2` 顶部用 `sb` 内联 padding；需要覆盖刘海、胶囊和不同 home indicator。

**建议**：
- 320 / 375 / 414px 三档必须验证：标题两行不破版、宽卡不横向溢出、多字频道可滚动、搜索面板不被键盘完全遮挡、最后一张卡能滚过底栏。

- 320px 若双列确实读不清，按 J7 再降单列；不要通过缩字号和缩间距硬保双列。
- 至少覆盖一台小屏 iPhone、一台大屏 iPhone、一台 Android；同时检查顶部胶囊和底部安全区。

**裁决**：J7。现阶段结论是“必须验证”，不是仅凭截图直接判死双列。

### D12｜P2｜动效降级与全局样式一致性仍需收口

**现象**：已有 `prefers-reduced-motion` 基础，但仍有关闭不完全的过渡和旋转；同时发现页后置样式覆盖了全局 Token，容易让同名的卡在不同页面/机型表现不一致。

**证据**：
- `app.wxss:52–56` 关闭了 `rise/screen`；`app.wxss:765–767` 关闭 FAB 闪烁和搜索粒子；但 `.fcard` 的 `transition:all .5s` 与 `.glass-press` 的 `rotateZ(1.7deg)` 未降级（`app.wxss:680–681`）。
- TabBar、sheet、detail 等仍有位移过渡；`fab-flicker` 在减少动态效果下会关闭，但默认仍持续闪烁。
- `transition: all` 会扩大属性监听范围，容易把布局属性也带入过渡；项目约定是关键帧只动 `transform/opacity`。

**建议**：
- 在减少动态效果下取消卡片旋转/缩放、面板位移和无限闪烁，保留即时状态变化与必要按压反馈。
- 普通态也建议把卡片按压缩小幅度降低，不再旋转；`transition` 明确列出属性，不用 `all`。
- 让 `.fcard` 只有一套权威样式来源；发现页特例放到页面作用域，浮层玻璃独立命名。
- 这些优化不一定改变截图，但能减少“同名组件在别处变样”和低端机动画掉帧的风险。

**裁决**：执行项。建议与 D02 一起处理，避免重复改同一批 CSS。
